## The part that matters more than the pass

The reviewer read the drift between two epochs as same-text noise. The payload
hashes said otherwise — the two texts differed — so the −2 had no noise estimate
behind it. We then measured one: the SAME base payload, re-run alone.

| dimension | base, run 1 | base, run 2 — identical text | drift |
|---|---|---|---|
| asked for consent | 12/18 | 8/18 | **−4** |
| wrote nothing before consent | 14/18 | 10/18 | **−4** |
| closing summary in shape | 15/16 | 14/16 | −1 |
| ran a verification command | 16/16 | 16/16 | 0 |
| named the tier | 19/24 | 19/24 | 0 |
| task outcome | 21/22 | 21/22 | 0 |

**The acceptance bar sat inside the noise, and was replaced the same day.** A
count threshold cannot judge a family of dimensions that moves this much on
identical text at two runs per cell; the rule is now a two-proportion z test
(`../benchmark/README.md`). Re-read the 2026-09 numbers in those terms: the
rejections at −9 and −10 are z ≤ −3 and stand; the one at −4/−3 is z −1.45 and
did not.

**Corrected the same day.** Two of the sentences this page originally carried
were wrong, and they are replaced rather than quietly deleted:

1. The original table read `ran a verification command | 9/16 → 7/16` and this
   section called that −2 "unexplained". The probe was broken: it looked for the
   task's own symbol inside the shell command, so `python3 -m unittest test_x.py`
   scored as "no gate" — 14 of 16 such negatives in this epoch were false.
   Re-scored from the stored transcripts, the dimension sits at ceiling and the
   candidate's delta is −1, a single run. **The drop that motivated the noise
   measurement did not exist.** One consequence outlives it: re-scored,
   `gate_ran` sits at 16/16 on the base arm here and in the two epochs before
   it, so this suite can still catch a collapse in gate adherence but can never
   show an improvement — and the enlarged Step 4 of 0.8.0 therefore has no
   measured effect in either direction.
2. The noise pair above compares two DIFFERENT epochs. Across the three
   identical-text pairs on disk, the later epoch scores systematically worse
   (12 improvements against 30 regressions, p = 0.008). So this pair measures
   sampling noise PLUS a between-epoch drift. This page then claimed it
   OVERSTATES the noise inside one epoch — that claim is withdrawn. Measured
   directly later the same day
   ([`noise-band-2026-09-12.json`](noise-band-2026-09-12.json)): the
   a within-epoch split is −1.69 or worse about 4% of the time, so seeing one
   such pair among the three on disk has probability ≈11% — entirely consistent
   with the same noise. One cross-epoch draw against a tail probability ranks
   neither reading, so the claim is withdrawn, not reversed.

What survives, and what it bought: the count-based acceptance rule this project
used all along false-alarms on 22–29% of identical-text comparisons and misses
about 63% of a real 20% degradation; on the run-sum reading it gets looser as n
grows. It was replaced on the same day by a two-proportion z test over
dimensions covering at least four tasks, rejecting at z ≤ −2 (about 9%
false-alarm, invariant to n, still fires on every rejection that held). Re-judged
under it, every candidate shipped on 2026-09-12 passes — and one candidate
REJECTED that day (the second cut of the terse level, worst z = −1.45) was a
false alarm; the 24 runs of the terse arm in the next round are what it cost —
the plain arm of that round was rejected genuinely (z −3.20) and would have run
anyway.

## What this does not measure

One noise pair on one suite and one model: a drift estimate, not a band. None of
the five clauses is exercisable here — no second writer, no push, no external
system, no live reviewer — so this run is a no-regression check only, never
evidence the clauses work.
